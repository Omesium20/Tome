# Architecture

Full detail behind the high-level summary in `CLAUDE.md`. Source of truth for scope/requirements is `PRD.md`; this document is source of truth for how the system is structured technically.

## System Overview

Two independent pipelines share a Next.js frontend, a FastAPI backend, and a ChromaDB vector store.

```
                    Next.js
                       |
                   FastAPI
                       |
                  LangChain
                       |
        --------------------------------
        |                              |
 Knowledge Pipeline          Deck Generation Pipeline
        |                              |
        --------------------------------
                       |
                  ChromaDB
```

- **Knowledge Pipeline** — runs offline, prepares Magic card knowledge.
- **Deck Generation Pipeline** — runs on-demand, builds decks using retrieved knowledge.

---

## Knowledge Pipeline

Transforms raw Scryfall card data into AI-readable knowledge. Offline process.

```
Scryfall → Card Import → Claude Metadata Generation → Normalized Database
  → Knowledge Document Generation → Hugging Face Embeddings → ChromaDB
```

1. **Card Import** — pull card data from the Scryfall Bulk Data API (oracle text, mana cost, color identity, types, legalities).
2. **Claude Metadata Generation** — Claude analyzes each card and generates strategic metadata (roles, themes, game stage, power rating, strengths/weaknesses, synergy tags). See `data-model.md` for the `CardMetadata` shape.
3. **Normalized Database** — Card + CardMetadata persisted as the source of truth.
4. **Knowledge Document Generation** — a natural-language document is generated per card from its Card + CardMetadata (not hand-written Markdown).
5. **Embeddings** — a Hugging Face Sentence Transformer embeds each knowledge document.
6. **ChromaDB** — stores document + metadata + embedding per card for similarity search.

### ChromaDB record shape

- **Document** — the generated knowledge document (text).
- **Metadata** — structured filterable fields, e.g. `{"name": "Cultivate", "colors": ["G"], "roles": ["Ramp"], "themes": ["Big Mana"], "mana_value": 3}`.
- **Embedding** — vector generated by the Hugging Face model.

## Deck Generation Pipeline

Runs synchronously when a user requests a deck.

1. **Receive selected cards** — the "build around" cards the user picked (e.g. `Hardened Scales`, `The Ozolith`).
2. **Generate retrieval query** — backend analyzes colors, themes, roles, and mechanics of the selected cards to build a retrieval query.
3. **Retrieve candidate cards** — ChromaDB returns ~100-200 similar/synergistic/supporting candidate cards.
4. **Claude deck construction** — Claude receives selected cards, candidates, user preferences (power level, collection preference), and Commander rules. Claude determines commander, strategy, win condition, ramp/removal/draw/protection packages, and lands.
5. **Deck validation** — Python validates 100-card count, commander legality, color identity, and singleton rules. On failure, errors are sent back to Claude for regeneration (loop until valid).
6. **Return result** — frontend displays commander, full deck list, owned vs. missing cards, proxy cards, and Claude's explanation.

### Division of responsibility

Claude **should**: understand strategies, recommend cards, build decks, explain decisions, select commanders.

Claude **should not**: search the card database, validate rules, track collections, calculate legality — these are backend responsibilities, enforced in code, not trusted to the model.
